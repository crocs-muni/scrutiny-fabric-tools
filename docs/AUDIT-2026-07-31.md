## 2. Confirmed correctness defects

### P1 — the resolve memo serves a stale overlay degradation (critical)

`overlayState` decides DEL-7's α/β from the **whole observed set** —
`byId.has(targetId)` at [resolve.ts:519](../packages/core/src/resolve.ts) — but `chainEpochTargets`
([store.ts:189](../packages/core/src/store.ts)) returns `[]` for a Binding and for any non-SCRUTINY
event, and for a Patch bumps only that patch's *own* root. `resolveRoot`
([store.ts:423](../packages/core/src/store.ts)) returns the cached resolution whenever
`chainEpoch[rootId]` is unchanged.

So an overlay anchored at root `R` whose `e reply` names an event outside `R`'s chain is classified
`orphaned/beta`, and the arrival of that target never invalidates `R`.

Reproduced end-to-end against the built package:

```
memoised store, target absent  : orphaned/beta
memoised store, target present : orphaned/beta
fresh store over same final set: orphaned/alpha
MISMATCH — memo says orphaned/beta, recompute says orphaned/alpha
```

This is a direct violation of **D29** ("every incremental path must agree with a from-scratch
recompute"), and of **RC-3**, which forbids serving stale bytes when fresh inputs are locally
available. It is also a **UR-1** confluence failure in effect: the reported state depends on arrival
order. D29 exists precisely to catch this class and does not, because nothing compares the memo
against a recompute for the overlay-degradation shape.

**Why it is not fixed here.** Every candidate fix changes epoch semantics, and epochs are **D24** —
a decision that needs a Corrections entry, not a patch. Options, cheapest first:

1. Include `observedEpoch` in the memo key for resolutions that contain any `orphaned` overlay.
   Correct and cheap; costs a recompute per ingest only for roots that actually have orphans.
2. Maintain an overlay-target → root index and bump those roots when a target id is first observed.
   Precise, but adds a third index to the reducer.
3. Drop the α/β distinction from the memoised value and compute it at read time from the live set.
   Smallest blast radius, but splits `Resolution` into cached and live halves.

Recommend (1). Note SG1 (store-level confluence) passes today because it compares a `StoreView`
projection that excludes resolutions.

### P3 — T2 carry-forward across an EOF-newline change (fixed)

`toLines` encodes the trailing newline as a final `''` element, so `lines.length` is
lines-plus-terminator. `shift` was computed from it, so a hunk that changed **only** the EOF newline
state (C5) moved `shift` by one having added and removed no lines. Every later T2 insertion landed
one position early — **silently**, because T2 has no uniqueness test the way T1 does, so the wrong
position applied cleanly instead of halting.

Measured, on the shipped code, from a payload built entirely by the shipped producer:

```
PRE-FIX  : applied "X\na\nb\nC"     <- insertion at index 0
POST-FIX : applied "a\nX\nb\nC"     <- correct
```

Wrong canonical bytes with a `status: 'applied'` verdict is the worst available outcome: **RC-3**
then obliges a non-UI consumer to serve them downstream.

**Why 10k round-trip cases never found it.** It needs the EOF-changing hunk to *precede* the
insertion in the payload — descending hunk order, which C8/T3 permit and which `makePatch` never
emits. The property test generates only its own producer's output. Pinned as
`t2/shift-after-eof-newline-change`.

*Correction to a sub-agent claim:* the reported reproduction used `@@ -1,0` and is masked by the
zero-clamp at [patch.ts:500](../packages/core/src/patch.ts); the defect is real but needs a
non-clamped index to observe.

### P5 — `createStore` performs no validation

`validateEvent` is referenced nowhere in `src/` outside its own definition and the barrel re-export.
`store.add` runs `options.verify` (SIG-1) and BD-7 endpoint typing, and stops there. A consumer using
the documented ergonomic entry point (D15) ingests and resolves malformed Bindings, mis-tagged
events, and PT-7-violating overlays.

This is not an oversight in isolation — `ValidateOptions.lookupEvent`
([validate.ts:40](../packages/core/src/validate.ts)) exists *specifically* so `store` can resolve
`pending` verdicts per §7.6, and the plan's own ownership table says validate "returns *pending*,
resolved by `store` per §7.6". That wiring was never built, and `Store` exposes no `lookupEvent` for
a consumer to build it themselves. Needs a phase: it changes what `add` accepts and what `AddResult`
reports.

### P6 — the in-memory storage `limit` is arrival-order dependent

[store.ts:550](../packages/core/src/store.ts) sorts by `created_at` with no `id` tie-break. `Array.sort`
is stable, so ties resolve to Map insertion order — arrival order. Two nodes with the same corpus and
different arrival orders get **different subsets** from the same limited filter. `resolve` is
order-independent; the event set handed to it is not, so UR-1 leaks through the storage port rather
than through the pure functions. One-line fix (`|| a.id.localeCompare(b.id)`), deferred only because
it belongs with P2's rework of the same function.

### P11 — zero-cost scans (fixed)

`patternChars` summed line **lengths**, so a pattern of empty lines billed 0 while `occurrences`
still ran `|L| × |oldPat|` comparisons. Now charges one unit per line.
*Correction to a sub-agent claim:* the reported "64 uncharged scans" overstates it — the first such
hunk HALTs on `ambiguous-match`, so chaining requires each empty pattern to be unique. Real, narrower.

## 3. The coverage machinery had a hole (P4, fixed)

The project's stated countermeasure against protocol drift is *generated, CI-enforced rule coverage,
not discipline* — and its rule-citation discipline says **no link in the chain is hand-written**.

For the V layer that holds: `v-coverage.test.ts:21` derives its expected set from the registry, so an
unclassified V rule fails the build. **Every A/D gate instead compares its table against an `OWNED`
array hand-transcribed from the plan's module-ownership table** — for example
`a-build-coverage.test.ts:15`, whose own comment claims it is "machine-checked against the plan's
assignment, so a rule cannot be silently dropped". The check is circular: it can only catch a rule
the transcription already knows about.

Measured: **21 real rules (plus reserved OV-1) were in no coverage table at all.** Six of them —
`PR-2/3/4`, `MD-2/3/4` — are actively emitted by `validate.ts:206-230`, making them the only rules in
the package that `issue()` can produce with no coverage entry anywhere. D34's claim was false for
exactly those six.

Fixed in `a69a249`: `rule-closure.test.ts` asserts `union(every table, _unowned.ts) == registry`;
`_a-validate-coverage.ts` picks up the six; `_unowned.ts` declares 13 genuinely-unowned rules with
written reasons; `RL-4` filed under `patch` (which enforces it structurally — `PatchLimit` has no
`content` field, so caching abandoned bytes is unrepresentable); and the TR-1 roll-up in
`invariants.test.ts` now includes the `admit` and `query` tables, which escaped it silently because
both are all-`not-covered` today.

Now: **139 rules — 126 owned by a module, 13 declared unowned with a reason.**

### The ownership table is unreliable, beyond the P2 case

`QUERY-BUILD.md` §2.2 resolved one double-listing (P2). It is a symptom. Full cross-product against
all 139 rules and every module's source:

- **Range notation over-claims.** `validate`'s cell says `E1…E6` and `build`'s says `P1…P4`. `E4`
  appears **only** in `build.ts:132`, zero occurrences in `validate.ts` — the identical defect to P2,
  never noticed because nobody expanded the range. `P3` is emitted by `validate.ts:591` and never
  touched by `build.ts`, yet `_a-build-coverage.ts` declares it `notCovered` on build's behalf.
- **The `events` row is a 17-way duplicate of the `validate` row.** All 17 rules it claims are also
  claimed by `validate`; seven of them (`TAG-4/5`, `VER-2/3/4`, `PR-5`, `MD-5`) appear nowhere in
  `events.ts`. There is no `_a-events-coverage.ts` at all. Same shape for `id`/`SIG-1`.
- **Seven silent omissions**, including `TR-1` — the invariant the entire severity model rests on,
  owned by everything and listed under nothing.
- **Three rules assigned to `store` are claimed by other tables**; `RL-3`'s only real emission is in
  `patch.ts:405`, a module the table says does not own it.

Recommendation: generate the ownership table from the coverage tables rather than maintaining it by
hand — the same "derive, never duplicate" rule D36 already applies to docs. Until then the table is
documentation, not a specification, and no gate should transcribe it.

## 4. Hazard #4 — re-measured against the real corpus

Corpus: `investigations/sec-certs-mapping/data/main-dataset.json`, 6,737 certs.

| Figure | Measured |
|---|---|
| Product roots | 6,737 |
| Product `content` bytes | min 156 / **median 287** / p95 447 / max 2,088 |
| **Realistic chain depth** | **0 or 1 — max 1.** The only Patch in the mapping is a status transition; maintenance updates map to Metadata+Binding, not Patch |
| Shared PP hubs / binding edges | 218 with fan-out ≥2 across 5,016 edges (**D39's "~217 / ~4,984" verifies**) |

Retained heap, Node 25.6.1, `--expose-gc`, forced GC before each sample:

| depth | baseline corpus | eager `ChainState` | lazy `resolve()` |
|---:|---:|---:|---:|
| **1 (real)** | 18.16 MB | **3.68 MB** | **2.73 MB** |
| 16 | 129.96 MB | 32.97 MB | 4.24 MB |
| 64 | 487.45 MB | **206.91 MB** | 11.02 MB |

**The 216 MB reproduces — at depth ≈67, not at "sec-certs scale".** The driver is the quadratic
`applied[]` arrays, not content strings. At the corpus's real depth the eager/lazy gap is **0.95 MB**.

Two things follow. First, **D28's byte-bounded LRU is over-engineered and was never built** —
`resolve.ts:327` interleaves overlay classification with the chain walk and retains only the running
content, and `RESOLVE.md:211` already argued this. The LRU can be struck from D28 rather than
implemented. Second, the number that actually matters is unmeasured by anyone: **the raw event corpus
at ~1.35 KB/event and 30k–110k events is 40–150 MB**, 15–50× the entire caching question, and it is
what decides whether a mobile tab survives.

**Browser: still not measured.** No headless browser is installed. Chrome ships pointer compression
that Node here does not, so these figures are conservative upper bounds for a tab — but hazard #4's
literal sentence remains true and should be re-scoped to the corpus, not the cache.

## 5. Comparative analysis

### Inside Nostr — extending D19

D19 measured one cell per library ("may it honestly assert `verified: true`?"). Verified afresh
against each project's default branch on 2026-07-31; storage shape and filter construction are new.

**D19 is now wrong in one cell.** welshman's `netContext.isEventValid` — recorded as "a mutable
global" — no longer exists; `packages/net/src/context.ts` holds only `{pool?, repository?,
getAdapter?}`, and verification is a per-request injectable with a safe default. That is an upgrade,
and D19 should be corrected rather than left to mislead.

NDK's verdict stands and its third defect's *mechanism* is refined: not an unbound
`validationRatioFn` but one **bound to the wrong object** — `.bind(this)` binds `NDK`'s method to the
relay, which has `lowestValidationRatio` but not `initialValidationRatio`, so the ratio becomes `NaN`
and `shouldValidateEvent()` returns `false` permanently, per relay. Observable behaviour is exactly as
D19 recorded.

**New, and stronger than what D37 already records about applesauce:** `EventStore.add` files a kind-5
deletion *before* the verification branch, and `DeleteManager` checks only that the claimed author
matches. An **unsigned** kind 5 carrying a victim's `pubkey` is accepted and thereafter suppresses
that victim's events. That is a better reason for D37's "do not use applesauce's `EventStore`
defaults" than the kind-5-removes-the-target behaviour already cited.

Consequences worth acting on:

1. **D18's "required `verify`, no default" is vindicated by the only counter-examples available.**
   Every library that supplies a default verifier has a reachable path to zero verification — NDK via
   the `NaN` ratio, applesauce via `verifyEvent = undefined` *and* the kind-5 early return, nostrify
   via a custom `NPoolOpts.open`. A required parameter is the one construction none of them evaded.
2. **D20 re-verified verbatim.** nostr-tools inserts the *declared* id into `_knownIds` before
   parsing and returns early; welshman's `tracker.track` precedes `isEventValid`. **nostrify is the
   ecosystem's only verify-then-dedup ingest path** and is worth naming as such.
3. **`createInMemoryEventStorage` is the weakest store of the five that have one** — one `Map`, no
   indexes, a fresh full materialisation per filter object, plus an uncached deletion scan per query.
   Defensible for v0.1 under D37's swappability, but it should be *stated*, not discovered.
4. **Do not copy welshman's index design as-is.** `_applyAnyFilter` picks the first applicable index
   in fixed priority and never intersects. Every filter `query.ts` emits carries both
   `#t:[FABRIC_TAG]` and `kinds:[SCRUTINY_KIND]`, so the tag index returns the entire corpus — an
   index whose commonest key holds 100% of rows is worse than none. The useful discriminators here
   are `#i`, `#e`, and `#t` restricted to the *event-type* tags.
5. **NDK's memory cache defaults to `maxSize: 5000` and evicts silently** — directly below our stated
   ~6,737-event working set. Any `examples/adapters/ndk` must pass `maxSize` or not exist.
6. **No library ships a typed filter builder.** `query.ts`'s named constructors are a genuine
   ecosystem gap — and the gap is *safety*, not expressiveness: welshman has the richest filter
   algebra and its `intersectFilters` **unions** its array fields, while `trimFilter` silently
   shuffles and truncates over 1000 entries.

### Outside Nostr — git, OT, CRDT

The brief's framing needed one correction: **`git apply` refuses context *reduction*, not
*relocation*.** `find_pos()` in `apply.c` walks the entire image outward from the `@@` hint and
returns the first match, with no uniqueness check and a forward bias on ties. `patch(1)` defaults to
**fuzz 2**, discarding two context lines before giving up. So the industry default *is* silent
relocation, and citing git as the strict counter-model overstates it.

Placing `patch.ts`: it is **`git apply` plus a uniqueness proof** — identical on atomicity,
whitespace and no-3-way, and strictly stronger on exactly one axis. It is also structurally immune to
git's whole CRLF class, because it never touches a filesystem (PB-1/PB-2).

On CRDTs: refusal-based determinism is **the right call, and the reason is architectural**. T1 is not
a merge policy — it is a *base-integrity assertion*. The canonical chain is a linear, single-author
replay against an exactly-known base (CHN-1), so a non-matching hunk is evidence the producer diffed
a different base, never legitimate divergence. Git's offset search exists to tolerate drift between a
mailed patch and a moved-on tree; that condition cannot arise here. And the two places SCRUTINY *does*
have concurrency it already refuses to merge on principle (§7.2 self-fork freeze; §7.3 "No
protocol-level merge happens") — git-merge's position, not Automerge's arbitrary-but-deterministic
winner. Adopting a CRDT would mean replacing the unified-diff payload with identity-bearing
operations (Yjs `ID(clientID, clock)` + `origin`/`originRight` + tombstones), destroying the "a patch
is a patch" property, to automate a decision §7.3 has assigned to a human.

**What refusal costs, and the actionable consequence.** It loses exactly the edits whose pattern
legitimately occurs more than once — ~0.3% of prose at context 3, but **5.8% at zero context**, and
worse on the tables and repeated `| field | value |` rows SCRUTINY actually targets. That cost is
payable producer-side and currently is not: `makePatch` fixes `context = 3` because P1 says
`min(3, available)`, but **P1 is a SHOULD about count and says nothing about uniqueness**. Proposal
(not implemented — it changes producer output): widen `context` iteratively until every hunk's pattern
occurs exactly once in `before`, falling back to the P4 warning only when even full-file context
cannot disambiguate. No spec change needed; P1's three lines are a floor, not a ceiling.

## 6. Decisions this audit makes

### 6.1 The conformance-vector gap — do not keep drifting

Appendix G.1 names four files. `application.json` (46 cases) and `validity.json` (19) are vendored
and digest-matched; `discovery.json` and `serialization.json` are reserved and **absent from both
repos**. The spec says so explicitly (`protocol-spec.md:1469`), so this is acknowledged incompleteness,
not drift. But "we'll rely on substitute gates" has now been the answer for six consecutive phases,
and the D-layer corpus is empty while 31 D-layer rules exist.

**Decision, three parts:**

1. **Contribute `serialization.json` upstream.** It is the cheap, objective one: §3's event-id
   serialization is `JSON.stringify` by ecosystem definition (R11), `id.ts` already implements it, and
   a vector is just `event → serialized string → sha256`. No policy judgement is involved and this
   project is the reference implementation. There is no reason for it to stay reserved.
2. **Formalise the project-local corpus.** `patch-regressions.ts` is *already* written "shaped to
   become conformance vectors verbatim once the corpus exists". Emit them as a vector-shaped JSON
   artifact so the substitute gate becomes exportable, and so it can be offered upstream as the seed
   of a real corpus rather than staying a private test fixture.
3. **Report the actual blocker on `discovery.json` rather than writing it.** D-layer vectors cannot
   be built in `validity.json`'s shape, because §6.0 gives D rules no disposition — which is exactly
   why `admit`'s and `query`'s partitions are legitimately all-`not-covered`. A vector format asserting
   "what outcome?" has no outcome to assert for a D rule. That is a **spec** gap and belongs in
   SPEC-FEEDBACK, not in a file this project invents unilaterally.

Rejected: relying on substitute gates indefinitely. They are good — G1–G4/AG1–AG4/SG1–SG5/BQ-1–6 found
real bugs — but P1 above is precisely a gap none of them covers, and a gate suite designed by the same
people who wrote the code has a known blind spot that an external corpus does not.

### 6.2 `artifacts` — drop it as a numbered phase

Hazard #1 called it "the weakest unit"; D7 said it "may never ship". The audit owes a verdict and the
corpus supplies one: **the real sec-certs content has a median of 287 bytes and a maximum of 2,088** —
nothing in it approaches §4.6's ~30 KB `imeta` threshold. The motivating consumer does not exist.

**Decision: remove Phase 9 from the plan's numbered sequence.** Keep D7's shape decision on record for
whenever a consumer appears; re-open only when one presents an artifact over the threshold. One thing
must be preserved either way, and is now enforced: **IM-4 is a MUST** ("warn before displaying
unverified artifacts"), so `core` must never grow *partial* imeta support — shipping IM-1..3 without
IM-4 would be a conformance failure. IM-1…IM-4 are recorded in `_unowned.ts` with that reason, so the
closure gate will now surface the decision if anyone starts.

### 6.3 RL-1 / IX-1 / IX-2 / IX-4 — the P4 pattern generalises to two of the four

`build.ts`'s P4 self-check is the project's one example of a producer-side SHOULD getting a real
structural check. It transfers exactly as far as the data in hand:

- **RL-1 — implemented.** §5.4's bounds table has four entries and `build.ts` can compute **three** of
  them from the template it just assembled: tag value ≤ 1024 bytes, signed event ≤ 64 KB (the signer's
  `id`/`pubkey`/`sig` addition is a fixed 285-byte constant, so the bound holds without core ever
  seeing a key), and hunks per payload ≤ 64. The fourth — patches per chain ≤ 1000 — is genuinely
  invisible to a module that sees one event, and stays with RL-2/RL-3 on the consumer side.
- **IX-2 — implemented, and it was never truly unowned.** Its substance is already enforced on
  receipt at `validate.ts:207`, citing the co-extensive siblings `PR-2`/`MD-2`. What was missing was
  the *producer* side: `buildProduct`/`buildMetadata` would happily emit 500 `i` tags. Now warned.
- **IX-1 — declined.** "Canonical `i` tags for what the event is *about*" needs an oracle for
  aboutness only the publisher has. The one decidable proxy (warn on zero indexers) would fire on
  events the spec explicitly permits: "Publishers who omit `i` tags rely on content search."
- **IX-4 — declined.** Distinguishing indexers a payload *mentions* from those it is *about* requires
  parsing the payload, which this package deliberately never does. IX-2's ceiling is the mechanical
  proxy for the same intent.

Both emissions are `warning`: RL-1 and IX-2 are D-layer and TR-1 forbids a D rule rejecting a V-valid
event. `invariants.test.ts` asserts this.

**A note on the general question.** The reason the P4 pattern transfers to these two and not the other
two is not "SHOULD vs MUST" — it is whether the predicate is decidable from the builder's arguments.
That is the test to apply to any future producer rule, and it is the same test §6.0 states for V-layer
membership ("could a consumer holding the event tell?"), applied on the producer side.

### 6.4 D6 — confirm, do not reverse

The comparative analysis produced one argument *for* publishing adapters: writing one is not trivial,
because `EventFilter` needs a real converter (§7, C2 — three independent type blockers), so four
copy-paste adapters would each reimplement it. But the right response is to **fix the filter shape**,
after which an adapter is a thin transport wrapper again and D6's reasoning holds unchanged. Reversing
D6 to work around a defect we are already fixing would be the wrong trade.

**D6 stands. Phase 12 stays contingent, and Phase 7 is additionally blocked**: `RelayTransport` does
not exist. `interfaces.ts` declares only `TrustProvider` and `EventStorage`; the transport interface
lives solely in the plan's D16 table. "Adapters" cannot be built against an undefined interface.

## 7. `EventFilter` is not a NIP-01 filter (P2)

`query.ts:4` states the module "returns plain NIP-01 filter objects"; `index.ts:147` and the plan's
own module table repeat it. It does not. NIP-01 filters are **flat** — `{"kinds":[…],"#t":[…]}` —
while `EventFilter` nests them under a `tags` key (`interfaces.ts:60`).

Relays ignore unrecognised filter members. Demonstrated against a NIP-01 matcher:

```
query.ts filter as sent : {"kinds":[39701],"tags":{"#t":["scrutiny-fabric"],"#i":["cve:CVE-2017-15361"]}}
  matches -> a,b,c (3/3)          <- every constraint silently dropped
correct NIP-01 filter   : {"kinds":[39701],"#t":["scrutiny-fabric"],"#i":["cve:CVE-2017-15361"]}
  matches -> a (1/3)
```

Every filter the module emits degrades to "all kind-39701 events" — including the loss of the
`#t:["scrutiny-fabric"]` constraint that **DQ-1 makes mandatory**. `deletionsFor` degrades to every
kind-5 event on the relay. This is the mirror image of the dead engine's VER-4 bug: that one silently
dropped events by over-constraining the filter, this one silently drops the *constraints*.

It is latent today only because nothing sends it to a relay yet, and because
`createInMemoryEventStorage`'s own matcher reads `filter.tags` — so the in-memory store honours a
shape no relay will, which is what has kept the tests green.

**The stated rationale is also wrong.** `interfaces.ts:47-51` says `tags` is "kept as a named field
rather than a template-literal index signature so it can coexist with `kinds`/`since`/`until`/`limit`'s
differing value types." Compile-tested under the repo's own TS 5.8 `--strict`: the flat shape with a
`` [tag: `#${string}`] `` index signature compiles clean alongside all of them. nostr-tools, NDK and
nostrify all use exactly that shape.

Two further blockers a Phase 7 adapter will hit, both confirmed by compiling against the real `.d.ts`:
our arrays are `readonly` and theirs are mutable; and **an `interface` never receives an implicit index
signature in TypeScript**, so even a flat `interface` is rejected — the type must be a `type` alias.
Also: `tags: Record<string, …>` permits multi-character tag names that no relay and none of the three
libraries can express, so a converter cannot be total.

**Proposed as its own phase** (public surface: `EventFilter` is exported from the barrel and consumed
by `EventStorage.query`). Scope: flip to the flat shape as a `type` alias, drop `readonly` on the array
members, keep `search`, and re-point `matchesFilter`. Fix P6's tie-break in the same pass.

## 10. Ergonomics — the three a first consumer actually hits

1. **There is no way to get a trust-filtered view out of a `Store`.** `CreateStoreOptions` does not
   take a `TrustProvider`. Rendering overlays under OV-7 — the commonest client operation — requires
   `visibleOverlays(res.overlays, trustedView(toIndex(store.getState().admit)))`: four imports from a
   second module, routed through `getState().admit`, a field whose own doc comment calls it internal
   cache plumbing. Meanwhile `computeAdmission(events, trust)` is the *only* consumer of
   `TrustProvider` in the package and is unreachable from the store path — so D21's interface requires
   implementing `version` and `deltaSince`, which nothing calls, to use a function the store never
   calls. Two parallel trust mechanisms, neither documented as the recommended one.
2. **The first call is a wall.** `createStore` requires `verify` with no default (correct, D18/D12) —
   but the package exports nothing to build one. `eventIdMatches` covers the id half; the Schnorr half
   has no helper, no type, and no worked example. Hello-world cannot compile until the consumer
   independently discovers `@noble/curves`.
3. **`buildPatch` has six positional parameters including two transposable pairs.** `root`/`reply`
   and `before`/`after` are same-typed; swapping `before`/`after` yields a perfect inverse patch that
   **passes P4 self-verification** against the wrong baseline. Separately, that self-check calls
   `applyPatchContent` with no `ApplyOptions`, so it always runs at default ceilings regardless of the
   consumer's configuration — a 70-hunk patch returns `status: 'limit'` and is reported as a *P4
   producer-correctness* failure, conflating a resource limit with a correctness one in the one module
   that has no parameter to fix it. (P11's new hunk-count warning now at least names the real cause.)

Also on the public surface: `HaltReason`, `LimitKind` and `ApplyOptions` are load-bearing in
`ChainState`, `Annotation`, `ResolveOptions` and `CreateStoreOptions`, and **none is exportable** —
D32 correctly keeps `patch.ts` out of `exports`, but the types it owns still need re-exporting (P10).
`resolveRoot` names two different public functions. `EndpointRef` and `ETagRef` are the same concept
with different field names (`authorPubkey` vs `authorHint`), so round-tripping build output through
`eTags` renames a field.
